# DTU crop, cameras and reconstruction

The D1 adapter accepts DTU SampleSet’s calibrated, radially corrected RGB photographs at lighting setting 3. Each original 1600 × 1200 image uses the central 1200 × 1200 square starting at (200, 0). Pillow downsamples it to 256 × 256 with Lanczos. The source files are untagged eight-bit RGB. D1 treats their delivered RGB values as display-sRGB for comparison with the published scorer. It applies no colour fitting, exposure correction or additional undistortion. The resulting view covers the central crop. [DTU MVS data and citation](https://roboimagedata.compute.dtu.dk/?page_id=36)

## Which cameras correspond to the photographs?

DTU’s SampleSet ReadMe assigns colour to the right camera. Its supplied `cal18/pos_NNN.txt` matrices project points in the structured-light reference frame of the left camera into each right-camera rectified image. The original MATLAB evaluation maps a raw distance of 10 to the end of its 10 mm colour scale. The camera adapter therefore converts world translations from millimetres to metres. The right-camera calibration MAT file also contains an 11-unit checkerboard grid. Bouguet’s documented pixel coordinates place (0, 0) at the upper-left pixel centre. The numerical audit reports 0.0614 original-pixel coordinate RMSE for 7,056 raw right-camera calibration corners and 1.0019 pixels after adding one to both axes. Expressed in the original first-left-camera frame, the 49 independently fitted right-camera centres differ from the supplied rectified P centres by 0.52–3.13 mm. The corresponding left-camera differences are 190.09–195.24 mm. The raw lens calibration and rectified projective matrices serve distinct image versions. [DTU SampleSet](https://roboimagedata.compute.dtu.dk/?page_id=36) · [Bouguet camera model and pixel convention](https://robots.stanford.edu/cs223b04/JeanYvesCalib/htmls/parameters.html)

The adapter decomposes each supplied rectified 3 × 4 projection, retains its full focal lengths and principal point, and applies the image sampling transform to K. With crop offset `x0` and scale `a = 256/1200`, the output principal point is `a * (cx - x0 + 0.5) - 0.5`. The vertical calculation uses `y0`. For source s00 the measured output is `fx=617.030619, fy=615.077436, cx=132.556741, cy=131.674926`. The original text projections round their coefficients to six decimals. The adapter records the resulting tiny skew and verifies that dropping it to match the zero-skew scorer changes every sampled projection by at most 0.005 cropped pixels. Across ten cameras and 210 off-axis points at three physical depths, the largest measured discrepancy was 0.0000231 pixels.

View selection used the 49 available calibration entries common to both objects at lighting 3. The ranking compares endpoint angle, baseline relative to convergence range, baseline direction, ray separation and the normalized camera layout with Stage C. The crop, camera IDs and metric transform were registered before the first photograph download. Both M2 and M4 use the same endpoints. M4 adds two available positions, including an elevated original camera. The selected endpoint span is 0.24424 m / 23.077° compared with Stage C’s 0.72000 m / 20.433°.

The canonical frame uses the midpoint between the two endpoints’ closest forward-axis points. Its x axis is their mean image-right direction. Its y axis is their mean optical-forward direction with the x component removed. The right-handed z axis completes the basis. A rigid translation places the aim point at (0, 0.4, 0.85) m, the fixed Stage C prior-box centre. The official physical range to the convergence point is 0.61051 m. Both forward and inverse metric transforms are recorded. Extra photos, target colours and scans have no role in this calculation.

## Capture and output

`scripts/dtu_camera.py` takes just the original calibration files, article metadata, SampleSet directory listing and published Stage C rig. It emits `camera-plan.json`, `cameras.json`, `crop.json`, `metric-frame.json`, `view-set.json`, `projection-checks.json` and separate source/render calibration for each condition. The independent checkerboard test uses `scripts/dtu_camera_checkerboard.py`. These accept SciPy for reading MATLAB calibration archives. The 256-pixel conversion and ordinary CPU deployment use NumPy and Pillow.

`scripts/dtu_handoff.py convert` takes a sealed download run, object ID and role. The converter checks every selected original member name, CRC, byte size and SHA-256. It writes either the four source images and `source-images.json` or six separate target photographs and `references.json`. All cropped RGB pixels are included in the image-domain comparison. DTU’s 3D observation mask provides no verified image-space object segmentation. Reference photographs require a separate access receipt on the external object, after the deployment outcomes for both conditions have been recorded.

`scripts/dtu_handoff.py batch` packages source-only M2 and M4 jobs. The Windows command is `python -B worker/scripts/dtu_reconstruct_windows.py --batch-sha256 HASH --store STORE --returns OUT`. The original Stage C gsplat 1.5.3 optimizer starts with 4,096 common float32 Gaussians seeded by PCG64 at 43171, takes 256 whole-source updates and retains its fixed topology. Each condition consumes 16,777,216 source pixels, with 128 updates per source for M2 and 64 for M4. A separate renderer renders all allowed source and six target cameras from the same final checkpoint. A separately registered set1-only diagnostic restarts from the same initialization for 1,024 updates and compares source and target RGB endpoints.

`scripts/dtu_render.py` runs a depth, opacity and absolute pixel-centre probe for each actual transformed camera on the CUDA rasterizer. It measures the expected camera-axis Z for two overlapping translucent layers, unnormalized depth, nonzero opacity, an off-axis isolated point and an empty pixel. The gsplat call receives the actual calibrated K with 0.5 added to its two principal coordinates. It writes raw float32 display RGB, opacity and normalized expected depth in metres. A pixel without foreground opacity carries NaN depth. The metric depth here is a prediction; this experiment has no first-surface depth label.

`scripts/dtu_case_record.py build` rechecks both Windows seals, all source bytes and trace entries, checkpoint identity and the independent source-image/self-render residual. It emits the established `case/case.json` alongside `case-provenance.json` and `reconstruction-readback.json`. The public 057 development example ran through the same case construction and source-crop identity path. All released source, camera and predicted members matched their original hashes. The finite features and every missing/support mask matched at all six target views for both M2 and M4.
